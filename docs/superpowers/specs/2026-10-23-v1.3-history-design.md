# v1.3 — History & Corrections: Design

## Intent and why

Today, when a session ends, the app drops the queue master back on the setup
screen and everything recorded — leaderboards, games, shuttles, attendance —
becomes invisible. v1.3 makes history a first-class surface: browse past
sessions, review each session's leaderboard, games log, shuttles and
attendance, and see a per-player career page. v1.4 (partner synergy,
fairness report, streaks) will build directly on these pages and queries.

The second half of v1.3 is **corrections**: recorded data is sometimes wrong —
a misclicked score, wrong shuttle count, the wrong player dragged into a
lineup, a check-in that shouldn't exist. Corrections work both **live**
(during the session) and **after the fact** (from history), through the same
UI and the same endpoints.

## Goals

1. **History browser** (`#/history`): list of past sessions (most recent
   first) — name, date, court count, players attended, matches played,
   shuttles used.
2. **Session detail page** (`#/history/:id`): final leaderboard, games log
   (every match with players, scores, shuttles, duration, rating), shuttle
   totals, attendance list. Works identically for the **live** session — the
   header gains a link to it — and updates in place via the existing SSE
   subscription.
3. **Player career page** (`#/players/:id`): all-time games, W/L, win rate,
   point differential, hours on court, partners played with (with W/L
   together), and per-session attendance history.
4. **Attendance tracking**: attendance derives from `queue_entries` (who was
   checked in per session); the career page shows attendance % per calendar
   month.
5. **Corrections** on any ended match (live or historical): edit scores,
   shuttles, rating, and the players in the lineup; delete an accidental
   match. Attendance corrections: remove a wrongly checked-in entry, add a
   missed check-in.
6. **Export**: download the session detail (leaderboard + games log +
   attendance + shuttles) and the career page as CSV or JSON, one click each.

## Non-goals (v1.3)

- No partner-synergy/head-to-head *analysis* views (v1.4) — but the career
  page's partners list is the groundwork.
- No editing of live/active matches (abort already exists for those).
- No auth or permission gating on corrections (consistent with the app today).
- No multi-session pagination concerns beyond simple "most recent first"
  listing with a reasonable limit (the club has decades of disk space and
  hundreds of sessions at most — full list is fine).

## Anti-goals (a failure even if it technically works)

- A correction that silently leaves derived stats wrong (leaderboard,
  `games_played`, `total_seconds_played`) — the fix must be atomic.
- History pages that disturb the live queue-master screen (no layout, focus,
  or SSE regressions).
- Corrections that can move a player into a match they weren't checked in for.

## Constraints

- Same stack: Hono server, SQLite (bun:sqlite), React SPA, no new runtime
  dependencies. Hash-based client routing is written by hand in App.jsx — no
  router package.
- SSE `broadcast()` fires after every correction so all connected tabs update.
- The database is append-friendly but not migrated: no new columns on
  existing tables needed for v1.3 (correction history/audit is out of scope).
- Tests follow the repo policy: API-level server tests for every endpoint and
  rule (`bun run test:server`), browser specs only for UI re-render
  assertions.

## Decided (the how)

### Data preservation (builder check finding — user-ruled)

- **Session end no longer deletes anyone.** Today `PATCH /sessions/:id/end`
  calls `resetPlayersToPreset()`, which erases every player not in
  `players.json` along with all their matches and queue entries. From v1.3,
  session end keeps the preset resync parts only — resync preset skill
  levels, re-add missing preset players, prune preset players not seen in any
  session — and **never deletes a player who has match history**. Drop-in
  players persist in the pool and can be removed by hand in setup.
- Eligibility for attendance % therefore keys off `players.created_at`, which
  is now stable (players aren't re-created).

### Routing and pages

- Hand-rolled hash routing in `App.jsx`: parse `location.hash` → view state
  (`#/history`, `#/history/:id`, `#/players/:id`); `popstate`/`hashchange`
  listener re-renders. Unknown hash → live/setup view (current behavior).
- The live view and setup screen are unchanged except: header gains a
  **History** link (only when a session exists); the games-log access for live
  corrections is the session detail page (current session id).
- Session detail page = same component for live and ended sessions. Pages
  **fetch** their data (`GET /api/sessions`, `GET /api/sessions/:id/detail`)
  and treat an SSE broadcast as a refetch signal — the 1-second broadcast
  payload is NOT grown with the games log (the live queue-master screen must
  not pay for it). Ended sessions render once.

### Source of truth and recompute

- **History/career/export stats query `matches` directly** (joining
  `queue_entries` for player identity), never the denormalized
  `queue_entries.games_played` / `total_seconds_played`. The leaderboard query
  in `computeLeaderboard` already does exactly this and is reused.
- After any correction (player move, match delete), affected `queue_entries`
  rows get `games_played`, `total_seconds_played`, and `last_played_at`
  **recomputed from `matches`** inside the same transaction:
  `COUNT(*)` / `SUM(ended_at - started_at)` / `MAX(ended_at)` over ended
  matches containing the entry. This keeps the live rotation logic (wait
  priority, rest rules) correct without a full-session rebuild.
- Entries currently `playing` an active match are excluded from recompute
  (only ended matches count).

### Correction endpoints

- `PATCH /api/matches/:id/correct` — ended matches only (`ended_at IS NOT
  NULL AND state = 'active'`). Body (all optional, at least one required):
  `team1_score`, `team2_score`, `new_shuttles`, `used_shuttles`, `rating`,
  `players: [p1, p2, p3, p4]` (singles: exactly 2) — **in-order slot mapping**:
  doubles `[team1_p1, team1_p2, team2_p1, team2_p2]`, singles
  `[team1_p1, team2_p1]`. Side permutation is an accepted correction (teams
  entered backwards is exactly the kind of mistake this fixes); the confirm
  dialog is the explicit intent. Validation:
  - `players` must be existing `queue_entries` of the match's session, unique,
    matching the match's format (2 = singles, 4 = doubles), and not currently
    playing an *active* match.
  - Same integer/range validation as `PATCH /:id/end` (scores 0–99, rating
    1–5, shuttles ≥ 0).
  - On success: update the row, recompute affected entries (old set ∪ new
    set), `broadcast()`.
- `DELETE /api/matches/:id` — **extended** to also accept ended matches
  (delete an accidental match outright): entries recomputed, `broadcast()`.
  The current abort semantics for live matches are unchanged.
- Attendance:
  - `POST /api/sessions/:id/attendance` — body `{ player_id, checked_in_at? }`
    (default now). On a **live** session this delegates to the existing
    check-in logic (alphabetical `sort_order` + `virt_offset` inheritance — a
    bare INSERT would corrupt queue ordering and rotation fairness); on an
    **ended** session it inserts a plain row with status `left`. Duplicate
    check-in for the same player+session → 409.
  - `DELETE /api/queue/:entryId` — **extended** to work on ended sessions;
    refuses (409) when the entry appears in any match (fix the match instead).
- All corrections are single transactions; all fire `broadcast()`.

### Career page

- `GET /api/players/:id/career` returns: identity; totals (games, wins,
  losses, win rate, point diff, hours = SUM(ended_at − started_at)); partners
  list (each partner with games/W/L together) across all sessions; and
  attendance: per session (name, date, games played) plus per-month
  attendance % (sessions attended in month ÷ sessions that month that the
  player was eligible for — eligibility = the player existed in the roster at
  that session's date; **builder call**: sessions before the player's
  `created_at` count 0% and are excluded from the denominator).
- `#/players/:id` renders it; player names anywhere in history link here.

### Export

- `GET /api/sessions/:id/export?format=csv|json` — session detail: leaderboard
  rows, games log rows, attendance, shuttle totals. JSON = the same payloads
  the page uses; CSV = one file with clearly separated sections (comment
  lines starting `#`), leaderboard first. `Content-Disposition: attachment`.
- `GET /api/players/:id/career/export?format=csv|json` — career payload.
- Client: plain `<a href>`/fetch → blob download buttons; no dependencies.

## Left to the builder

- Exact UI layout of the history browser / session detail / career pages —
  follow the existing dark-theme card/table idioms in the codebase.
- CSV column ordering within each section.
- The games log row's edit affordance (inline vs. modal) — a modal reuse of
  the end-match form fields is expected.
- Date/time formatting helpers (reuse whatever `StatsSidebar`/`Header` use).

## Review Focus (for the later implementer)

1. **Recompute correctness**: after swapping a player between two matches,
   both entries' games_played / total_seconds_played / last_played_at equal a
   fresh aggregate over ended matches — write the API test that proves it.
2. **Correction while players are queued**: a player moved out of a historical
   match who is currently `playing` an active match must not be disturbed
   (status untouched; only ended matches count toward recompute).
3. **Attendance delete refusal**: deleting an entry that appears in a match
   409s — and the UI says why.
4. **Singles vs doubles**: `players` array length must match the match's
   format; a 4-player array on a singles match is a 400.
5. **Export shape stability**: JSON export is exactly the page payloads (no
   divergence); CSV opens in a spreadsheet with leaderboard/games/attendance
   sections intact.
