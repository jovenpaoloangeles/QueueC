# v1.2 — Smarter Matching: design

**Date:** 2026-10-22
**Source:** ROADMAP.md v1.2 items; ROADMAP is the spec of record for scope wording.

## Intent

Three roadmap items:

1. **Target optimizer (doc'd, not built)** — implement the optimizer design in
   `docs/algorithm.md` behind the dry-run-first gate.
2. **Rotation rule config** — "no more than 2 consecutive games" / "rest N games
   minimum" as session settings the heuristic respects.
3. **Partial-lineup lock** — keep drafted players when re-running Smart Match
   instead of discarding them.

## 1. Target optimizer — already shipped; verify and tick

The two-stage ε-lexicographic engine described in `docs/algorithm.md` is
**implemented** in `server/logic/smartQueue.js` (`planBatch`), wired through
`server/routes/automatch.js` behind the same `dry_run` / `slate_only` gates, with
the post-spec additions (Hard Anchor, Bench-First) noted in the algorithm doc's
status header. Sweep-tuned ε parameters and a simulation harness
(`tests/sim/epsilon-sweep.mjs`) exist.

**Work for this item:** a conformance pass only — read the shipped engine against
the algorithm doc's five structural guarantees (§1) and the Stage A/B metric
tables (§4), note any drift in the algorithm doc's status header, and check the
ROADMAP box. **No behavior change. No rebuild.** If the conformance pass finds
the doc and code disagree materially, stop and surface it rather than "fixing"
either side.

## 2. Rotation rule config — two per-session settings

Mirrors the v1.1 `checkin_order` pattern: set at session creation, stored on the
session row, consumed server-side.

### Settings

| Setting | Column | Type / default | Meaning |
| --- | --- | --- | --- |
| Max consecutive games | `sessions.max_consecutive` | `INTEGER NOT NULL DEFAULT 2` | `c_i < C_max` — a player at or above this consecutive-game streak is ineligible (unless graceful relax fires). |
| Rest N games minimum | `sessions.rest_games` | `INTEGER NOT NULL DEFAULT 0` | Hard bench: a player is ineligible until **N completed matches** (session-wide) have finished since the match they last played in. `0` = off (today's behavior). |

`rest_games` is **game-count-based, not time-based** (decided by the human
partner; the roadmap wording "rest N games minimum" was taken literally over the
engine's existing 8-minute streak-reset timer, which stays as an internal
`MATCH_CONFIG` constant unchanged). Counting is per session history, ordered
oldest→newest by `started_at, id`: for each player, find the index of the last
history entry containing them; the player's `gamesRested` is the number of
entries after it. A player with no games played rests `0`. Multi-court endings
resolve naturally because the count is over the shared session log, not wall
time.

Defaults equal today's behavior: `max_consecutive: 2` is the existing constant
and `rest_games: 0` disables the new hard bench, so existing sessions and fresh
defaults are behavior-identical.

### Server

- `server/db.js`: migration adds both columns when missing (same
  `PRAGMA table_info` guard style as `checkin_order`).
- `POST /api/sessions` (`server/routes/sessions.js`): accept both fields;
  validate `max_consecutive` integer 1–5, `rest_games` integer 0–3; invalid →
  400 with a message, same shape as the `checkin_order` validation.
- `POST /api/sessions/:id/automatch` (`server/routes/automatch.js`): pass
  `{ maxConsecutive: s.max_consecutive, restGames: s.rest_games }` into
  `planBatch`'s existing `cfg` override (merge already exists in
  `planBatch` — `const C = { ...MATCH_CONFIG, ...cfg }`).
- `server/logic/smartQueue.js`: **one addition** — the unary filter (Module 1)
  gains the `restGames` check: after the consecutive-limit filter, players with
  `gamesRested < C.restGames` are removed, computed from the history array
  already passed in. The graceful relax may still override it when fewer than 4
  players are eligible (same rule as the consecutive limit — the
  anti-starvation fallback wins over both hard constraints). The time-based
  `minRestMinutes` stays in `MATCH_CONFIG` untouched (it feeds
  `consecutiveCounts`).

### Client

- `client/src/components/SetupScreen.jsx`: two controls next to the existing
  check-in-order select — a 1–5 select for consecutive games and a 0–3 select
  for rest games ("off, 1, 2, 3"); both default to 2 / off; sent in
  `createSession` payload.
- `client/src/api.js`: `createSession` passes the fields through (verify it
  forwards the payload body as-is).

### Docs

`docs/usage.md` (setup section) and `CHANGELOG.md` get a line each.

## 3. Partial-lineup lock — Smart Match fills around your picks

**Surface:** the On Deck builder only. Both entry points ("✨ Smart add" on the
strip, "✨ Smart Match" in the builder) route through `runSmartFill` →
`handleSmartFill` → a slate-only dry run, whose first slate is poured into the
builder's four slots. Today that pour replaces the builder wholesale. Court
drafts have no Smart Match re-run and stay out of scope. Already-slated On Deck
lineups stay out of scope.

### Server

`POST /api/sessions/:id/automatch` request body gains:

```json
{ "dry_run": true, "slate_only": true, "locked": [101, 205] }
```

- `locked`: array of queue-entry ids, **0–3 of them** (a locked 4th would leave
  nothing to plan), each of which must be a currently-waiting entry in this
  session; anything else → 400 `{"error": "..."}`. Duplicates rejected. Honored
  only together with `slate_only: true` — a `locked` request without it → 400
  (the feature's surface is the builder; court-match automatch stays as-is).
- `computePlan` forwards `locked` to `planBatch`.

**`planBatch` contract addition** (`server/logic/smartQueue.js`):

- New optional param `locked: number[]` (default `[]`).
- **Locked ⇒ exactly one quartet.** With a non-empty `locked`, the planner
  produces a single quartet containing all locked ids (the builder consumes
  `slate[0]` only, so planning more quartets would be waste). Unary/window
  rules: locked players bypass the consecutive-limit and rest-games filters and
  the bench-first exclusion, and the candidate window is the union of the top-K
  slice with all locked players (so a locked long-waiter outside top-K is still
  planned around).
- **Bands apply within the locked set:** the Stage A ε-cascade (wait sum →
  virtual games → skill variance) computes its best/band over the quartets that
  contain all locked ids, not over all quartets — so locking a fresh-off-court
  player (low wait) doesn't let the max-wait band eliminate every
  locked-containing quartet. Hard anchor likewise evaluated only among locked
  quartets. If no quartet contains all locked ids, the planner returns no
  matches (client shows its existing "Nothing to add" path — no error invented,
  no band relaxed).
- Stage B unchanged — a locked pair may partner or split; scoring decides.

### Client

- `handleSmartFill` sends `locked` (the builder's current non-null picks) with
  the dry-run call; `client/src/api.js` `autoMatch` passes the body through.
- The builder pour maps returned ids into slots by id: picks stay in the slots
  the QM chose; only empty slots receive new players. If the planner returns
  nothing (pool too small / locked ids not co-plannable), keep the builder as-is
  and toast the existing "Nothing to add — need 4 waiting players" info (reworded
  to mention the locked picks).
- Both Smart add buttons are disabled when all four builder slots are filled
  (nothing to plan; today's wholesale replace would surprise).

## Goals / non-goals

**Goals:** flexible rotation knobs per session; Smart Match respects hand-picks
instead of wiping them; optimizer conformance documented.

**Non-goals:** live-editing rotation settings mid-session (same as
`checkin_order`); rotation settings per court; banning pairs UI (the `bans`
param exists but has no surface — untouched); Smart Match for court drafts;
re-running Smart Match on an already-slated lineup; any engine rewrite.
**Accepted edge (decided):** the 2–3-waiter singles fallback (`suggestPlayers`)
has no streak/rest logic and stays without it — a session with strict rotation
settings can still field a rested-out player in the singles fallback. Documented
in `docs/usage.md`; closing it means wiring `cfg` through `suggestPlayers` and
is deliberately deferred.

**Anti-goals:** silently relaxing the rotation settings to force a quartet —
the graceful relax stays exactly as shipped (only when <4 eligible, and it
still prefers lowest streaks). Locked players never get forced onto a court
match; the feature is slate-only by construction.
